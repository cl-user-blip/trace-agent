# 面试讲解卡

## 90 秒介绍

“我做了一个能在本地运行的小型 Agent runtime，想解决的是工具调用以后状态如何可靠保存、失败以后如何恢复。我把 planner、权限校验、工具执行和持久化分开。工具结果、调用账本和 checkpoint 在 SQLite 同一个事务里提交，所以已经提交的步骤恢复时不用再做。

但我没有把这个说成 exactly-once，因为工具执行和数据库提交之间还有崩溃窗口。当前只有检索、读文件和安全算术三个只读工具；如果加支付或邮件，必须让外部服务支持幂等键。

默认 demo 用规则模拟器，零 key 可以跑。另有真实模型 tool calling 适配器，但我没在当前测试里调用在线模型，因此工程案例通过率和模型智能水平是分开报告的。现在有 11 个固定故障回归案例，还有权限、预算、并发提交和崩溃窗口的单元测试。”

## 可以现场演示的三个点

1. `python -m trace_agent demo`，打开 `out/demo/paused/index.html` 和 `out/demo/index.html`，说明哪个事件提交后进程才可以安全停止。
2. `python -m trace_agent evaluate`，打开 HTML，展示 transient retry 和永久权限错误为何走不同路径。
3. `python -m pytest -q tests/test_runtime.py`，说明 crash-before-commit 测试为什么期待工具被调用两次，这正是对恢复语义的诚实验证。

## 追问与回答要点

**为什么不用 LangGraph？**

这个项目目标是把核心语义写到可审查的最小实现中，先理解 graph 框架在检查点、重试和持久执行上解决什么。此实现只支持串行工具环；需要并行分支、人工介入、分布式调度时，成熟框架的价值会更明显。

**checkpoint 放在工具执行前还是后？**

两个位置都需要。执行前保存 pending action 与调用 ID，保证恢复执行同一个动作；执行后原子保存结果和新状态，保证下一步看见一致观测。调用前保存不等于外部操作已经发生。

**并发调用同一个 run 会怎样？**

revision 乐观锁避免陈旧状态覆盖，但工具执行发生在事务之外，可能先重复执行再在提交时冲突。当前约束是一个 run 一个 worker。下一步用带到期时间的租约控制执行权，并对写工具依然使用外部幂等键。

**怎样证明工具是安全的？**

我能给出明确的边界测试：工具白名单、参数 schema、路径解析、文件大小、AST 节点和数值限制。它不是操作系统 sandbox；可信本地目录被恶意进程并发改写的竞态仍是边界外问题。模型侧提示注入也不能靠一句 system prompt 证明安全。

**引用校验能消灭幻觉吗？**

不能。这里检查的是来源行曾被读取，而不是主张被来源支持。下一步会把答案拆成主张，以标注的 claim–evidence 数据集独立评估 citation correctness、coverage 和 abstention。保留集应和开发用文档/问题分开。

**离线通过率为什么是 11/11？会不会没有意义？**

这是固定工程断言的回归通过率，问题很小，而且测试覆盖的是设计好的预期行为。它对防回归有价值，对智能泛化没有外推价值。我不会把它写成真实模型任务成功率，也不会声称有生产业务收益。

**模型 API 重试会不会重复花钱？**

可能。重试上限限制请求次数，但不能保证服务方未处理上一请求，也不能形成美元预算。真正的成本治理需要记录 usage、预估输出预算、服务提供方的幂等策略和统一限流。

## 简历表述模板

可在实际阅读、运行和修改项目后使用：

> 实现可恢复 Agent 工具调用状态机，使用 SQLite 原子保存结果账本、执行事件与 checkpoint；支持只读工具权限限制、有界重试、决策预算和带来源的执行轨迹。构建 11 个可复现工程回归案例并验证崩溃窗口与路径边界。

如果没配置并验证真实模型，不写“完成线上大模型 Agent 部署”；如果没有业务数据，不写“服务 XX 用户、降低 XX% 成本”。建议亲自加一个有独立测试的功能，例如文档 hash 校验或模型 usage 统计，然后把设计取舍讲清楚。
